# Architecture Decision Records

Append-only log of decisions made building this project — architecture, data
model, scope, process. Exists to answer "why was it done this way?" for future
maintainers and contributors.

## Conventions

- **Append-only.** Historical entries are never edited. A reversal is a new
  entry that references the entry it reverses.
- **ADR numbers** are permanent IDs, assigned in append order. **Dates** are
  decision dates. The two can diverge — e.g. ADR-0008 records a 2026-05-17
  decision that was appended after the 2026-05-19 entries.
- Promoted from an internal design journal on 2026-05-20 (see ADR-0009).

## Entry format

```
## ADR-NNNN — YYYY-MM-DD — Title
**Status:** Accepted | Superseded by ADR-NNNN
**Decision:** what was decided
**Context:** why this came up
**Alternatives considered:** options not chosen + why
**Implications:** what this constrains / enables downstream
**Reverses:** (if applicable) link to entry or doc being reversed
```

## ADR-0004 — 2026-05-19 — Three project tenets locked
**Status:** Accepted
**Decision:** Three guiding tenets adopted as project axioms.
1. **"It's just people."** Trace ownership chains toward natural persons via official sources. Where official trail dies, say so (trail-end honest). Unofficial extensions allowed only when explicitly labeled and out-of-scope for v1.
2. **Radical transparency.** Project is open source. Git history of pipeline repo = part of the data product, not internal hygiene. Design-journal + commit messages = audit trail for data-affecting decisions. We can't disparage opacity in our subjects while obscuring our own process.
3. **Extreme sourcing.** Every emitted fact links back to the most-granular official source available. Not "13F filing X" — link to *that table row*. Cross-DB combination and primary-source anchoring are co-equal pipeline goals, captured on the same record.
**Context:** Tenets articulated by owner while discussing seed-map plan. Surfaces the project's why: the subject is media opacity; the method cannot itself be opaque. "It's just people" reframes goal of the graph (people, not corporate boxes). "Extreme sourcing" sets provenance bar above typical aggregation pipelines.
**Alternatives considered:** Looser provenance ("source = filing-level URL") — rejected; loses the row-level honesty owner wants. Closed-source for early iteration — rejected; conflicts with transparency tenet.
**Implications:** Schema must support granular source anchors (row/section/page/cell where source publisher allows). Provenance is first-class table (already in `data-model.md` — confirmed). Source-tier field needed to distinguish official-direct vs official-derived vs (future) llm/unofficial. Repository hygiene matters more than typical (no rebase squashes that erase data-decision attribution).

## ADR-0005 — 2026-05-19 — v1 = automation-first, official-sources-only, no LLM
**Status:** Accepted
**Decision:** v1 pipeline restricted to standard automation against official structured data sources. **No LLM extraction in v1.** **No unofficial sources in v1** unless absolutely necessary (and labeled distinctly when admitted). Automation-first rule: even when manual data entry would be faster, automate.
**Context:** Direct corollary of Tenets 1 + 3. Hard divide between automated-on-official vs LLM/human-curated. Owner explicit: prove the automation works before any softer extraction admitted.
**Alternatives considered:** Keep LLM as second-pass fallback for malformed proxy tables (prior CLAUDE.md stack position) — deferred to v2; v1 must demonstrate official-source reach honestly first. Allow seed map data to ship as `human-curated` tier — rejected; seed map demoted to test fixture / verification ledger only.
**Implications:** CLAUDE.md stack section needs update (Anthropic API line currently lists LLM fallback). Coverage shrinks vs prior plan — accepted as honest cost. Seed map (`seed_map.json`) becomes scaffolding/fixtures only; pipeline must independently re-derive every fact from official extraction before emit. Approach: seed entry guides where to look, official extraction is what ships. Future v2 may admit `llm-extracted` and `unofficial-labeled` tiers via the source-tier field, but never silently mixed with official-direct.

## ADR-0007 — 2026-05-19 — Modular architecture: per-source extractors + traversal layer
**Status:** Accepted
**Decision:** Three-layer architecture:
- **Layer 1 — Source extractors.** Independent Python modules per data source (FCC LMS, SEC EDGAR, IRS 990 XML, …). Each owns its source's quirks. Common return contract: `(entities[], relationships[], provenance[], coverage_log)`. Each extractor emits raw source rows alongside canonical pipeline shape, both retained.
- **Layer 2 — Resolution / traversal.** Orchestrator. Implements the `domain → entity → parent → ultimate-parent → subsidiaries` walk. Calls extractors per traversal step. Doesn't know source internals. Same layer serves v1 (script feeds starter outlet list) and end-goal (server feeds URL-derived outlet identifier). Build now, even though v1 only invokes it from a script.
- **Layer 3 — Stage / resolve / export.** Shared. DuckDB staging tables (extractor output, common schema). Cross-source entity resolution + dedupe. Validation. SQLite export (idempotent).
**Context:** Architecture question: monolith vs per-category vs modular. Per-category rejected (category is wrong axis — outlets cross categories, source is the right axis: Comcast's broadcast+cable+digital all use the same SEC+FCC paths). Monolith rejected (each new source = surgery on every stage). Modular chosen, owner-leaned.
**Alternatives considered:** Per-stage plugin model (per-pipeline-stage plugins instead of per-source extractors) — overkill at 3 sources. Event-sourced facts table (immutable event log, current state = projection) — useful for end-goal write-back, deferred to v2.
**Implications:**
- Extractor contract is the only required abstraction. Three Python modules + a registry. No base class hierarchy.
- Traversal layer makes "private newspaper obscurity" near-free: iterate extractors, log "0 results" per source, emit trail-end. Architecturally identical to NYT — just empty results. Strengthens case for including private-newspaper category v1.
- End-goal flow (URL → answer) is not a re-architecture later. Same Layer 2, new entry point (server-driven instead of script-driven).
- Raw-row retention costs disk, buys auditability + Tenet 3 provenance anchors.
- `_model/data-model.md` extended with architecture section + provenance-tier fields.

## ADR-0008 — 2026-05-17 — Treat FCC schema PDFs as reference, not authority
**Status:** Accepted
**Decision:** `LMSchema.pdf` + `LM-ERD.pdf` are reference material only. Ground truth = the bulk `.dat` shape, verified empirically. Schema design draws from data probes + ERD cross-reference, never ERD-first.
**Context:** Both PDFs landed in `unfiltered_data/` alongside the bulk LMS dump. Prior guidance in `_model/data-sources.md` said `"READ BEFORE PARSING"` — that line predates discovery and is reversed by this entry. Discovery already found 14 fragility hits via OPIF API probe that the ERD wouldn't expose: sentinel-null variants (`"NO FRN"`, `"N/A"`), duplicate-row artifacts at the application layer, name-change-under-stable-FRN as a corporate event, free-text suffix encoding (`"DEBTOR-IN-POSSESSION"`), `SEE EXHIBIT` placeholder rows, M:N FRN↔entity. Published schemas describe intent; bulk data shows extraction reality, including legacy CDBS→LMS migration artifacts (2013 cutover).
**Alternatives considered:** Trust ERD as authoritative (cheap, fast — rejected; schemas-on-paper diverge from operational data, especially across legacy migrations). Skip ERD entirely (rejected; cheap reference for column-name canonicalization, enum hints, FK shape).
**Implications:** `_model/data-sources.md` guidance line flipped. ERD usable for: column-name canon, enum candidate lists, FK structure hints. Never final word on type, fill, or semantics. Adds explicit "verify bulk-dump parity" step to FCC stage. Generalizes: same posture toward SEC/IRS bulk docs when they appear.

## ADR-0010 — 2026-05-20 — Demote broadcast_group_map + pe_adviser_map to verification fixtures
**Status:** Accepted
**Decision:** `broadcast_group_map.json` (FCC licensee name → SEC CIK) and `pe_adviser_map.json` (PE firm name → Form ADV CRD) are removed as emitted/standing input config. Both bridge official source → official source; that mapping is derivable at runtime and must be. If kept at all, each is only a verification ledger / test fixture — the same status `seed_map.json` holds under ADR-0005 — used to validate the resolver, never to feed or short-circuit emitted output. `domain_map.json` is unaffected: it remains the one authoritative manual input (URL → entity has no official source, ever).
**Context:** Both maps cross official→official (FCC↔SEC, PE-name↔SEC ADV). FCC ownership reports already disclose the ownership chain within FCC; ultimate-parent name → SEC CIK is a lookup against SEC's published company index; PE firm → CRD is a lookup against the Form ADV bulk dataset (already downloaded). The project's purpose is to derive everything from official sources + accumulated DB; a standing hand-curated official→official bridge contradicts that. `pe_adviser_map`'s second job — scoping which PE firms are media-relevant — also dissolves: traversal reaches a PE firm via co-occurrence (ADR-0007), it is not pre-declared.
**Alternatives considered:** Keep the maps as emitted input config (original plan in `data-sources.md` / `external/data-download-checklist.md`) — rejected; hand-curation hides from the fuzzy-match problem for the top 20 and abandons the rest, and is reference beyond official sources. Drop entirely with no fixture — rejected; known-correct top-group bridges are valuable as a resolver test oracle.
**Reverses:** Map rows in `_model/data-sources.md` describing the two maps as pipeline inputs, and the corresponding items in `external/data-download-checklist.md`. `data-sources.md` updated in place; `external/*` is canonical and not modified (INV-17) — this entry records the reversal.
**Implications:** The FCC→SEC and PE→CRD bridges become runtime resolution (see ADR-0011). The fragility (FCC free-text name swamp — 14 discovery fragility hits) does not vanish; it moves from "curate around it" to "build a robust resolver + verification harness." Consistent with ADR-0005 — the pipeline re-derives every emitted fact independently. `_model/snapshot.md` manual-inputs list updated.

## ADR-0011 — 2026-05-20 — Resolution architecture: two-layer split + extractor resolve() contract
**Status:** Accepted
**Decision:**
1. **Two distinct resolutions, never conflated.**
   - **Resolution #1 — URL → entity.** Source-agnostic. URL-normalize → `domain_map` lookup → entity. Its own pre-traversal module, called by whatever the entry point is (v1 script, post-v1 server). Layer 2 traversal always receives an entity, never a URL. Deterministic — `domain_map` is a curated dict; no ambiguity, no pick-list.
   - **Resolution #2 — entity → source-local key** (CIK / FRN / EIN). Per-source. Lives in each extractor as `resolve()`.
2. **Extractor interface gains `resolve()`** alongside `extract()` (refines ADR-0007's contract):
   - `resolve(entity) → ResolutionResult` — `{ source_key | None, confidence, candidates[], provenance, method }`.
   - `extract(source_key) → ExtractorResult` — the existing `(entities, relationships, provenance, coverage_log)` tuple.
3. **SDK-confinement.** No source-specific SDK (`edgartools`, etc.) is imported outside its own extractor module. A source SDK is a data-fetch backend, not the definition of resolution. If resolution logic needs a source SDK, it is misplaced.
4. **Shared vs per-extractor split.** Shared (Layer 2/3 / common): URL normalization, `domain_map`, name normalization + aliases + `rapidfuzz` scoring, confidence rules, the `resolve()`/`extract()` interface, DB-cache lookup. Per-extractor: the call to the source's own search/data API, mapping source records → canonical contract.
5. **Five-tier resolution outcome model** — `resolve()` result drives handling: (1) 1 match high-confidence → auto-accept; (2) small set, no clear winner (≤ ~20) → human pick-list; (3) large/unfiltered set (> ~20) → resolution failure, query/filter broken; (4) 0 matches → trail-end honest (INV-19); (5) 1 match low-confidence → flag, never silently auto-accepted.
6. **Pick-list UX deferred to post-v1.** v1 resolution: unique-confident → accept; else flag / trail-end, no human ask. `ResolutionResult.candidates[]` exists from day one so the pick-list bolts on with no refactor.
**Context:** Resolution exists for UX — users paste a URL and never look up a CIK/FRN/EIN. Owner flagged refactor risk: if entity→identifier resolution is built inside an extractor coupled to that source's SDK, adding the next source forces a rebuild. The dangerous failure is not "too many candidates" but "confidently wrong" — one high-confidence answer that is wrong silently corrupts the graph; confidence calibration + the ADR-0010 verification ledger guard this, not the pick-list.
**Alternatives considered:** Single resolver conflating both resolutions — rejected; that is the coupling. A standalone resolution service with extractors registering `find_candidates()` — cleaner separation but overkill before 3 sources; revisit if source count grows. Lean per-extractor `resolve()` chosen.
**Reverses:** Nothing outright; refines ADR-0007 (extractor contract) and `_model/entity-resolution.md`.
**Implications:** `_model/entity-resolution.md` + `_model/data-model.md` updated with the resolution model. Two new invariants (SDK-confinement, two-layer resolution split). Thresholds (the ~20 ceiling), per-source matching strategy, and exact outcome handling are **provisional — to be tuned by stress-testing the resolver against real source data**, not finalized now. A human pick-list selection is a resolution act (which official filer is this entity), not fact authoring — facts remain auto-derived from the chosen official record — so INV-10 does not block the post-v1 pick-list; it needs a provenance note on the identifier link (deferred).

## ADR-0012 — 2026-05-21 — Final pipeline directory layout
**Status:** Accepted
**Decision:** Concrete directory/module structure realizing the three-layer architecture (ADR-0011, INV-27..32):
```
pipeline/                package root (renamed from main/)
  contracts.py           shared dataclasses — Entity, Relationship,
                         ProvenanceRecord, CoverageLog, ResolutionResult,
                         ExtractorResult. Dependency-free; imported by all layers.
  resolution/            shared resolution utils — names.py (normalize +
                         rapidfuzz), urls.py (URL normalize), confidence.py
                         (score → tier). Imported by extractor resolve() AND Layer 2.
  extractors/            LAYER 1 — __init__.py = source-name → module registry
    sec/                 resolve.py, extract.py, reference/ (source-local data)
    fcc/                 stub
  traversal/             LAYER 2 — url_to_entity.py (Resolution #1), walk.py
  staging/               LAYER 3 — stage.py, dedupe.py, validate.py, export.py
  run.py                 v1 entry point
config/domain_map.json   lone authoritative manual input (INV-32)
notebooks/               Jupyter scratch — recon spikes only (ADR-0002)
Makefile                 per-stage targets
```
- **`contracts.py` standalone, not inside `resolution/` or a `core/` dir.** Pure type definitions, no logic, imported by every layer — kept as one obvious dependency-free file.
- **Dir-per-source extractors, lowercase names.** `extractors/sec/` not a flat `sec_edgar.py`. A dir holds the resolve/extract split + source-local `reference/` data + room for source-specific helpers, and reinforces SDK-confinement (INV-30). Lowercase per Python module convention.
- **Source-specific reference data lives source-local.** `company_tickers.json` (SEC ticker→CIK index) → `extractors/sec/reference/`, not the package root. Only the pipeline-global authoritative input (`domain_map.json`) sits in `config/`.
- **Layer 3 = one `staging/` package, four modules.** Not four top-level dirs — avoids a `resolution/` directory-name collision with the shared-util dir, and keeps Layer 3 cohesive.
**Context:** ADR-0011 locked the resolution architecture but left the concrete file layout open — specifically where shared resolution utils and shared contract types live. Neither belongs to an extractor or to Layer 2 alone, since both import them. This entry resolves the active "final pipeline layout" task.
**Alternatives considered:** Single `core/` dir grouping contracts + utils — rejected; contracts are dependency-free types imported universally and read clearer as a standalone file. Four top-level Layer-3 dirs — rejected; `resolution/` name clash, less cohesive. Keep `main/` as package name — rejected; non-descriptive, unconventional for a Python package. Flat per-source module files (`extractors/sec_edgar.py`, the original `data-model.md` examples) — rejected; a dir-per-source carries source-local data + multi-file extractors and strengthens SDK-confinement.
**Reverses:** `_model/data-model.md` Layer 1 examples showing flat `extractors/fcc_lms.py` / `sec_edgar.py` / `irs_990.py`.
**Implications:** `_model/data-model.md` synced (Layer 1 examples + directory-layout block + `domain_map.json` path). No new invariants — the layout is an elaboration of INV-27..32. `main/extractors/SEC/index.py` retired to `notebooks/sec_recon.py` (recon scratch, to be rewritten clean against the contract). CLAUDE.md "Run" section still TBD — Makefile targets now stubbed, recipes pending. Scaffold created: 21 docstring-only module files.

## ADR-0013 — 2026-05-21 — External-IDs child table + evidence/provenance subsystem
**Status:** Accepted
**Decision:**
1. **External IDs → child table `entity_external_ids`.** One row per `(entity_id, id_type, id_value)`. Columns: `entity_id` FK, `id_type` enum (`frn` / `cik` / `ein` / `facility_id` / `crd` / …), `id_value`, `status`. The `entities` table carries zero source identifiers. INV-1 establishes FRN as M:N to entities (Bonneville: 3 FRNs ↔ 1 entity stack; Paramount: 5 names under 1 FRN) — an M:N relationship cannot be modeled as a set of nullable columns on `entities`.
2. **Evidence subsystem — four tables, replacing single-table provenance.**
   - `sources` — the source system itself (FCC LMS, SEC EDGAR, IRS 990). ~3 rows in v1. Carries `source_official` (bool).
   - `source_documents` — one specific filing / document. Carries the filing/publication date, which feeds INV-6 `last_verified`. One document is referenced by many provenance records.
   - `access_links` — how to reach a document; **many per document**. All three tiers stored, not just the most-direct: A = public URL, B = bulk-download URL + row id, C = our hosted mirror. Mirror-everything.
   - `provenance` — per-detail grain. Binds one extracted fact to one `source_document`. Carries the anchor (decision 3), the polymorphic target (decision 4), `extraction_method`, `extraction_code_sha`, `raw_source_row`, `confidence`.
   Reference shape: `provenance → source_document → source`; `access_links → source_document`.
3. **Anchor = typed payload, not wide columns.** `provenance` carries `anchor_type` (enum the pipeline controls), `anchor_payload` (JSON), `anchor_schema_version`. Each `anchor_type` has a documented payload shape (not DB-enforced); the interpret/validate logic for a type is written per-source, when that extractor is built. The anchor is the only structurally source-divergent part of a provenance record — three-zone model: common metadata (structured columns) / source-divergent anchor (typed payload) / raw source row (opaque blob, INV-28). A new source adds an `anchor_type` value + payload shape + interpret module; existing rows untouched, no migration.
4. **Provenance target = polymorphic.** `provenance` carries `target_type` (`relationship` / `entity_attribute` / `external_id`) + `target_id`. Per-detail grain (INV-3) plus extreme sourcing (INV-26) require entity attributes and external IDs to be sourced, not only relationships.
5. **Scope split + capture-or-lose, recorded as principle.** The pipeline is *witness/capture* — it records what was seen, where, and how. The website (separate repo) is *experience* — how that is shown to a user. The provenance schema serves capture only; display concerns never shape it. **Capture-or-lose:** at extraction time the pipeline must capture everything not reliably re-fetchable later — `raw_source_row`, anchor payload, all `access_links` including the mirror, and the fetch timestamp. Access state decays (a 2021 filing's public URL may be dead in 2027); the schema must hold all of it before the first extractor runs.
**Context:** Evidence/provenance was the largest open design thread (handoff focus). The trigger: structural divergence across sources — FCC LMS `.dat`, SEC proxy HTML/XBRL, IRS 990 XML share almost no structure — and owner's concern that a fixed provenance schema would either fail future/unofficial sources or force premature over-generalization. Resolved by separating provenance into three zones by divergence: only the anchor (the in-document locator) is genuinely source-divergent; common metadata and the raw row are not. Generalize only the anchor; design it for the three known v1 sources; let the `anchor_type` enum carry future sources additively. Over-generalizing now pays a real, present cost (lost cross-source validation, schema drift) to insure against sources that cannot be specified — the wrong direction, since fixing too-specific later is cheap and additive while fixing too-generic is expensive.
**Alternatives considered:** N nullable identifier columns on `entities` — rejected; INV-1's M:N relationship cannot be columns. Single-table provenance (prior `data-model.md` design) — rejected; cannot express per-detail grain, document reuse across many facts, or multiple access tiers per document. Store only the most-direct access link (prior INV-3) — rejected; violates capture-or-lose, access state decays. Wide-nullable anchor columns (`page`/`section`/`xpath`/`text_snippet`, the original ADR-0013 draft) — rejected; grows a NULL column per new source, the over-generalization trap in column form. Blob the entire provenance record behind a type discriminator — rejected; would bury `extraction_method`, tier, and dates that cross-source validation (INV-11) and the answer card must read uniformly.
**Reverses:** INV-3 "prefer most-direct link" → all access tiers stored (decision 2). INV-3 anchor shape "row/section/XPath/PK" → typed payload (decision 3). Supersedes the single-table `provenance` design in `_model/data-model.md`.
**Implications:** New invariants needed — external-IDs child table; four-table evidence subsystem; anchor typed-payload; all-access-tiers-stored; capture-or-lose; polymorphic provenance target. INV-3 to be rewritten for all-tiers + typed anchor. `_model/data-model.md` Provenance section rewritten and `entities` external-IDs row removed (done this session). `_model/invariants.md` + `_model/handoff.md` sync still pending. `pipeline/contracts.py` unblocked — `ProvenanceRecord` plus `Source`, `SourceDocument`, `AccessLink`, `ExternalId` dataclasses now finalizable against the locked schema. Per-`anchor_type` payload shapes are documented when each extractor is built, not specified here; v1 set = FCC LMS / SEC EDGAR / IRS 990.

## ADR-0014 — 2026-05-30 — Voting power deferred to v2; coverage gap tagging + EX-4.1 linking

**Status:** Accepted
**Decision:**
1. **v1 does not extract or compute voting power.** Ownership percentages by share class are emittable from structured XBRL (shares outstanding per class) + SC 13G/13D (holder percentages). Voting power requires a votes-per-share multiplier that is not tagged in XBRL and not extractable from the DEF 14A proxy table (edgartools parser returns empty). The multiplier lives only in unstructured prose — primarily in EX-4.1 (Description of Securities), a standard 10-K exhibit.
2. **v1 links to EX-4.1 directly.** For every dual-class entity, the SEC extractor captures the EX-4.1 exhibit as a `source_document` with `access_links`. The answer card can surface "Voting rights described in [Description of Securities](link)" — no extraction needed, trail-end honest per INV-19/20.
3. **Coverage gap tagging for deferred extraction.** The `coverage_log` (fourth extractor return value, INV-27) gains a `gap_reason` field — enum values: `not_available` (data does not exist in any known source), `unstructured_source_exists` (data exists but in unstructured form — extraction not yet implemented). Each gap entry carries a `source_document_id` pointing at where the data lives. This tag is the clean seam for v2: read gaps where `gap_reason = 'unstructured_source_exists'` → feed the linked documents to LLM extraction → write provenance records → close the gap.
4. **EX-4.1 is the preferred v2 LLM extraction target** for voting rights. ~9KB of legal boilerplate per company, standard exhibit location, consistent structure across filers. Much simpler target than proxy table HTML.
**Context:** SEC recon spike (step 1, filing-type survey on NYT) revealed: (a) `edgartools` DEF 14A `beneficial_ownership` table still returns empty — parser fix not landed; (b) XBRL `CommonStockVotesPerShare` concept is not tagged by NYT or META in the SEC CompanyFacts API; (c) inline XBRL in individual filings has per-class dimensional data for shares outstanding (via `StatementClassOfStockAxis`) but not for votes-per-share; (d) EX-4.1 contains the voting rights description in semi-structured prose at a standard, predictable location. The traversal fan-out (anchors → parents → subsidiaries → their parents, etc.) makes a manual lookup table infeasible — this is not ~18 entries but potentially hundreds. INV-10 (no LLM extraction in v1) and the scale of traversal together rule out all extraction paths for v1.
**Alternatives considered:** (a) XBRL `get_facts()` — CompanyFacts API strips dimensional context, and votes-per-share not tagged anyway. (b) Inline XBRL dimensional parser — ~50 lines, gives shares-per-class but not votes-per-share. (c) Manual votes-per-share lookup table — doesn't scale past anchor entities due to traversal fan-out. (d) LLM extraction of proxy table — ruled out by INV-10 for v1. (e) Treating voting power as `not_available` — rejected; the data *does* exist, just in unstructured form. A generic "unavailable" tag would lose the signal that this is extractable with better tooling, making v2 harder.
**Implications:** New `gap_reason` enum on `coverage_log` entries. `coverage_log` schema gains optional `source_document_id` FK. Inline XBRL dimensional parser (~50 lines) still worth building for per-class share counts — separate from this decision. EX-4.1 capture should be added to the SEC extractor's document-fetch list alongside the primary 10-K.

## ADR-0015 — 2026-05-30 — Relationship detail: typed-payload pattern + promote-everything principle

**Status:** Accepted
**Decision:**
1. **All queryable detail promoted out of raw blob.** `provenance.raw_source_row` is a verification backup only — a way to check if the pipeline made a mistake. Any data point that could be relevant to the frontend, to queries, or to downstream pipeline logic must exist in structured, queryable fields. The frontend decides what to display; the pipeline captures everything cleanly.
2. **Relationship rows gain a typed detail payload.** Same pattern as provenance anchors (ADR-0013 decision 3): `detail_type` (enum the pipeline controls) + `detail_payload` (JSON) + `detail_schema_version`. The `detail_type` discriminator tells consumers the payload shape. Each type has a documented payload schema (not DB-enforced); interpret logic written per-type when the extractor is built. New relationship types add a `detail_type` value + payload shape — existing rows untouched, no migration.
3. **Illustrative detail payload shapes (finalized per extractor, not here):**
   - `shareholder` — `{share_class, percent_of_class, shares_held, sole_voting_power, shared_voting_power, sole_dispositive_power, shared_dispositive_power, reporting_person_type, filing_date_as_of}`
   - `subsidiary` — `{jurisdiction_of_incorporation, percent_owned, consolidation_method}`
   - `insider` — `{position_title, transaction_type, shares_transacted, price_per_share, shares_post_transaction, is_direct_holding}`
   - `governance` — `{role, committee_memberships, term_start, term_end}`
4. **Universal fields remain on the relationship row.** `type`, `confidence`, `status`, `last_verified`, `qualifier` stay as structured columns — these are common across all relationship types. The typed payload carries only the source-specific detail that varies by type.
**Context:** SEC recon spike surfaced that SC 13G provides rich per-holder detail (share class, voting power split, dispositive power) that the existing thin relationship schema (`type` + `confidence` + `status` + `qualifier`) cannot carry. Owner's principle: "no data in the blob which can be relevant remains solely in the blob." The provenance anchor pattern (ADR-0013) already solved the identical problem — source-divergent data behind a type discriminator — for the in-document-locator side of provenance. This decision reuses that pattern for relationship detail. The alternative approaches (wide table with NULLs; child tables per relationship type) were considered but rejected for the same reasons as in ADR-0013: wide tables grow a NULL column per source, child tables multiply joins and complicate the Node.js server's query layer. The typed-payload pattern is proven in this project, additive, and keeps a single `relationships` table.
**Alternatives considered:** (a) Wide table — all possible detail columns on `relationships`, most NULL per row. Rejected: grows with every source, same over-generalization trap ADR-0013 rejected for anchors. (b) Child tables per relationship type (`shareholder_details`, `subsidiary_details`, etc.). Rejected: multiplies joins, complicates the Node.js query layer, no clear advantage over typed JSON for a ~100-entity v1. (c) Keep detail only in `raw_source_row`. Rejected: violates promote-everything principle — makes the blob a data store instead of a backup.
**Implications:** `relationships` table gains three columns: `detail_type`, `detail_payload`, `detail_schema_version`. `contracts.py` `Relationship` dataclass updated to include these fields. Per-type payload schemas documented when each extractor is built. `data-model.md` Relationships section updated to reflect new fields. The `qualifier` field (freetext) may become redundant for cases now covered by typed detail — evaluate per-extractor.

## ADR-0016 — 2026-05-30 — Unified provenance: gaps as provenance records, not a separate table

**Status:** Accepted. Amends ADR-0014 decision 3 (coverage gap tagging).
**Decision:**
1. **No separate coverage table.** Gaps are provenance records with `record_type = 'gap'`. One table to answer "what does the pipeline know about X?" — whether the answer is an extracted fact or a documented absence. The absence of information is itself a verifiable finding with a source document and a trail.
2. **`record_type` discriminator on provenance.** Enum: `extraction` (standard — extracted fact) | `gap` (data exists in source but not yet extractable). For gaps: `target_type = 'entity'`, `target_id` → the entity being investigated, `anchor_payload` carries `{data_point, gap_reason}`, `extraction_method` and `confidence` are NULL.
3. **`created_at` timestamp on every provenance record.** Pipeline run timestamp — when this record was written. Provenance records are immutable snapshots. Current state for a given target = most recent `created_at`. No `accessed_at` — verification freshness tracked by `last_verified` on the relationship row, not duplicated on provenance.
4. **Gap lifecycle is append-only.** When LLM extraction ships and fills a gap: write a new `extraction` record for the same target. The gap record stays — it's history. Current state = most recent record. No `superseded_by` FK, no status field on provenance — just timestamp ordering.
**Context:** Owner questioned whether gaps belong in a separate coverage table or in provenance. Key argument: the absence of data doesn't mean the trail to discover it doesn't exist — the reasons behind the absence tell a verifiable story. A separate table splits attention ("what do we know about voting power for NYT?" requires checking two places) and creates an ambiguous frontier (when does a partially-resolved gap graduate from coverage to provenance?). Unified approach: one table, one query, full history. The `record_type` discriminator adds minimal complexity — same pattern as `target_type` already on provenance.
**Alternatives considered:** (a) Separate `coverage_log` table (ADR-0014 decision 3 original design). Rejected: splits the "what do we know" query, creates graduation ambiguity. (b) Placeholder relationship rows with `status = 'gap'`. Rejected: clutters the relationships table with empty rows, mixes data-presence with data-absence. (c) `superseded_by` FK chain between provenance records. Rejected: over-engineered — timestamp ordering achieves the same result without the bookkeeping.
**Reverses:** ADR-0014 decision 3 (separate `gap_reason` enum on `coverage_log` entries). Gap tagging now lives in provenance via `record_type = 'gap'` + `anchor_payload.gap_reason`.
**Implications:** `provenance` table gains `record_type` enum column and `created_at` timestamp. `coverage_log` in the extractor return contract remains as an in-memory structure during pipeline runs (for orchestration/logging) but does not become a separate persistence table — gaps discovered during extraction are written as provenance records. `data-model.md` provenance section updated. ADR-0014 decision 3 superseded by this entry.

## ADR-0017 — 2026-05-30 — Local document cache: filings stored in original format

**Status:** Accepted
**Decision:**
1. **The pipeline caches every fetched source document locally in its original format.** The actual filing HTML, XML, JSON, or `.dat` file is saved to disk at extraction time. This is capture-or-lose (INV-38) applied to the documents themselves, not just the extracted data. If a SEC URL dies in 2028, the proof still exists locally.
2. **Linked via access_links Tier C.** The existing `access_links` table already defines three tiers: A (public URL), B (bulk-download URL + row ID), C (our hosted mirror). The cached file IS Tier C. A new `access_link` row with `tier = 'C'` points at the local file path. Full chain: provenance → source_document → access_links (Tier C) → file on disk.
3. **Storage layout, caching policy, and format normalization deferred to implementation.** Three open questions to resolve when the first extractor is built: (a) directory structure (by source + accession number? hash-based?), (b) cache everything we fetch vs only documents that produced provenance records, (c) byte-for-byte copy vs normalized. These are implementation details that should be tested against real data, not designed abstractly.
**Context:** Owner stated intent to save the actual filings alongside pipeline output so they can be linked from provenance and queried directly. This completes the capture-or-lose chain — `raw_source_row` on provenance captures the extracted slice, the document cache captures the full original. Both serve verification but at different granularity: `raw_source_row` proves what the extractor saw in a specific row/record, the cached document proves the full context that row lived in.
**Alternatives considered:** (a) Rely solely on `access_links` Tier A/B URLs to reach documents. Rejected: URLs decay — a 2021 filing's public URL may be dead in 2027. (b) Store documents in the SQLite database as BLOBs. Rejected: inflates DB size, complicates backups, wrong tool for file storage. (c) Store only `raw_source_row` per provenance record without full document. Rejected: loses the surrounding context — a provenance record proves one fact, but the full document proves the fact wasn't cherry-picked.
**Implications:** Pipeline needs a document cache module (likely in Layer 1, called by each extractor). Cache path convention needed before first extractor ships. `.gitignore` must exclude the cache directory. Disk usage scales with number of entities traversed — estimate for v1: ~100 entities × ~5-10 filings each × ~100KB-3MB per filing ≈ 50MB-3GB. Manageable.

## ADR-0018 — 2026-06-09 — DEF 14A ownership extraction: two-pass design, funds deferred, error taxonomy

**Status:** Accepted
**Decision:**
1. **Two-pass extraction for DEF 14A beneficial ownership.** Pass 1: `edgartools` `beneficial_ownership` DataFrame. If non-empty, use it. Pass 2 (fallback): HTML table parser with header-signal matching + numeric detection. Two complementary paths — edgartools covers ~47% of filings alone, HTML parser covers another ~43%, combined coverage ~90%+. Cross-validation opportunity where both paths return data.
2. **Funds, trusts, and ETFs deferred to v2.** Fund proxies have structurally different ownership sections (dollar ranges instead of share counts, per-fund breakdowns, notice-only filings). ~141 of 290 extraction misses in batch testing were fund/trust entities. Different parser needed — not worth building for v1 scope (operating companies).
3. **Two terminal extraction states.** `extracted` (got data) and `extraction_failed` (didn't). No "legitimately empty" category. If a filing exists and the pipeline returned nothing, that's a pipeline problem to fix in future versions. We own every gap. Future versions may triage which failures are truly empty sources vs parser limitations once coverage improves.
**Context:** Batch test of all 3,630 2026 DEF 14A filings. Results: 3,271 ok (90.1%), 290 no ownership tables found, 65 text fallback, 3 no HTML tables, 1 parse error. Investigation of the 290 misses found: (a) `edgartools.beneficial_ownership` is not always empty as previously assumed — returns data for 71 of 355 non-ok filings and 47% of ok filings; (b) HTML parser header signals miss common variants ("percentage of class" vs "percent of class", "% of total common stock"); (c) ~106 of 290 are funds/trusts with different proxy structures. Three fixes already applied during batch testing: unicode junk strip, `_filing_html is None` fallback to `_filing_text`, `read_html` ValueError handling.
**Alternatives considered:** (a) Single-pass HTML-only with broadened signals. Rejected: edgartools already parses many filings correctly — duplicating that work is waste, and edgartools updates will improve coverage for free. (b) Build fund-specific parser for v1. Rejected: different structure, small audience overlap with v1 target outlets, diminishing returns. (c) Three-way error taxonomy (`extracted`/`no_data_available`/`extraction_failed`). Rejected: can't reliably distinguish "source has no data" from "parser can't find it" without exhaustive manual review. Defaulting to "our problem" is more honest and creates correct incentive to improve.
**Implications:** SEC extractor module needs a two-pass dispatch path. Fund/trust detection needed at runtime (company name heuristic or filing metadata) to skip gracefully. Batch test script (`notebooks/proxy_ownership_batch.py`) captures the exploration results — findings inform extractor design but notebook code does not migrate directly into pipeline.

## ADR-0019 — 2026-06-09 — Two-mode traversal: bounded answer cards, unbounded graph extraction

**Status:** Accepted
**Decision:**
1. **Two traversal modes sharing one graph.** Mode 1 ("answer card"): fast, narrow — straight-line UP to parent company, surface existing data, seconds. Mode 2 ("full map"): exhaustive UP-then-DOWN traversal across all branches and indirect connections, runs offline, minutes/hours, builds the persistent ownership graph over time. The answer card reads FROM the graph; the full map BUILDS the graph. The card does not wait for the map — it uses whatever has been discovered so far and gets richer as the map fills in asynchronously.
2. **Full-map traversal has no artificial depth cap.** The graph is traversed until exhausted. Non-media entities (e.g. a pharmaceutical company discovered because Vanguard holds both it and a media company) exist as traversal nodes with full provenance. They do not get answer cards in Phase 1, but their ownership data is stored and queryable. The Phase 1 scope cap (~100 outlets, 18 anchor parents) constrains which entities get answer cards, not which entities enter the graph.
3. **13F-HR is a candidate for the DOWN leg from institutional holders.** Structured XML format, low extraction complexity, gives "what does this fund own" — the complement to DEF 14A's "who owns this company." Filing type selection for next recon spike remains open (13F-HR vs 10-K Exhibit 21 vs 13D/G).
**Context:** Owner identified that the traversal model (UP to parent, DOWN through subsidiaries/holdings) naturally discovers entities outside the media scope. A fund like Vanguard holds ~5,000 companies — going DOWN from Vanguard via 13F-HR creates entities for all of them. The graph explosion concern is real but manageable: the answer card is a scoped view over the graph, not the graph itself. Extraction runs unbounded; display is bounded. This clean split means the pipeline captures maximum data (INV-38 capture-or-lose) while the frontend controls what users see. Time budget difference: ~10 seconds for an answer card vs potentially minutes for a full traversal update.
**Alternatives considered:** (a) Cap traversal depth at N hops. Rejected: arbitrary limit loses legitimate indirect connections. If two media companies share an institutional holder, that connection is real data worth capturing. (b) Only traverse from entities in the Phase 1 target list. Rejected: misses cross-pollination — a single fund lookup reveals connections across many targets simultaneously. (c) Separate databases for answer-card data vs full graph. Rejected: one graph, one provenance chain. Display filtering is a frontend/query concern, not a storage concern.
**Implications:** Layer 2 traversal needs a mode parameter (fast/exhaustive). INV-29 already planned for dual entry points (script vs server) — this adds the time-budget dimension. Entity table may need a flag or view to distinguish "in scope for answer cards" from "exists as traversal node." Graph size will grow significantly beyond the ~100-outlet target — storage and query performance should be considered but are not blocking for v1.

## ADR-0020 — 2026-06-14 — 13F-HR extraction: pre-compute, daily sync, edgartools-native

**Status:** Accepted
**Decision:**
1. **13F-HR data is pre-computed into the SQLite artifact by the pipeline, not fetched live.** The full institutional holdings dataset for relevant filers is extracted during pipeline runs and stored in the output database. The answer-card fast track reads this pre-computed data; it never hits SEC EDGAR on the user request path. The full-map async job extends coverage by processing additional filers from a queue.
2. **Daily sync check for new filings and amendments.** A lightweight daily job queries SEC EDGAR for new 13F-HR and 13F-HR/A filings since the last run. On ~350 days/year this returns nothing (filings are quarterly, clustered in a ~2-week burst window 45 days after quarter end). During burst windows, new filings are fetched, parsed, and upserted. Amendments (13F-HR/A) can appear anytime and are caught by the same daily check.
3. **V1 scope: latest quarter only, filtered to filers holding seed media securities.** The pipeline extracts holdings from institutional managers that hold at least one security matching the seed media ticker/CUSIP list. Estimated v1 filer count: 200–500 (out of ~6,000 total 13F filers). Full-universe extraction and historical backfill are deferred to post-v1 temporal-tracking phase. No schema change needed for backfill — same tables, additional `report_period` values.
4. **Extraction uses `edgartools.ThirteenF` class — no custom XML parsing.** The `edgartools` library provides first-class 13F support: `ThirteenF.infotable` returns a DataFrame with columns (Issuer, Class, Cusip, Value, SharesPrnAmount, InvestmentDiscretion, OtherManager, SoleVoting, SharedVoting, NonVoting, Ticker, Type, PutCall). The XML info table is parsed automatically for both standalone and combination reports. Raw XML preserved via `.infotable_xml` for provenance anchoring.
5. **Aggregation by (Cusip, filer CIK) required.** Combination-report filers (e.g. BlackRock: 30 sub-managers) produce multiple rows per security — one per sub-manager with different discretion types. The pipeline aggregates to total position per filer per security for relationship records, while preserving per-sub-manager detail in `detail_payload` (per INV-41).
**Context:** Recon spike (2026-06-14) tested `edgartools` ThirteenF against two filers: Vanguard (17,686 holdings, 3.7s extraction time) and BlackRock (50,651 holdings, combination report with 30 sub-managers). Both parsed cleanly. MCP sweep confirmed SEC EDGAR MCP tools provide cover-page metadata only — actual holdings data requires `edgartools` XML parsing. FMP 13F API is plan-gated (inaccessible). Tested reverse lookup: given ticker FOXA, confirmed Vanguard ($1.79B), BlackRock ($1.16B), State Street ($1.15B), Fidelity ($207M) all discoverable by iterating known major holders. 13F universe is bounded (~6,000 filers filing quarterly) and the XML is consistently structured — unlike DEF 14A's HTML parsing ambiguity.
**Alternatives considered:** (a) Live-fetch 13F data on user request. Rejected: 13F filings are large (50k entries for major funds), SEC rate-limited (10 req/s), and quarterly-static — no benefit to re-fetching what hasn't changed. Pre-compute is cheap (~12 minutes for 200 filers, ~30 minutes for 500) and data only updates quarterly. (b) Filter to media-only holdings at extraction time. Rejected: full portfolio enables relative-position context ("8% of Fox is BlackRock's 47th largest holding") which enriches answer cards. Filtering happens at query/display time, not extraction time. Consistent with ADR-0019's "graph captures everything, display is bounded." (c) Custom XML parsing of the 13F info table. Rejected: `edgartools` already handles both XML and TXT formats, resolves tickers, handles combination reports. No value in reimplementing. (d) Use FMP or other third-party API for 13F data. Rejected: FMP plan-gated, introduces external dependency, loses provenance chain to original SEC filing.
**Implications:** SEC extractor module (Layer 1) needs a 13F sub-extractor alongside the DEF 14A sub-extractor. Shared infrastructure: Company lookup by CIK, filing retrieval, rate limiting. The daily sync job is a thin wrapper: query for new filings → filter to relevant filers → extract → upsert. CUSIP-to-entity resolution is a new requirement for Layer 2 — edgartools resolves CUSIP→ticker, but ticker→entity mapping needs the existing `domain_map` or a new `security_map` (deferred to extractor implementation). The `other_managers` field on combination reports provides a sub-manager graph that could feed entity resolution (30 BlackRock subsidiaries with CIKs) — capture in entity records at extraction time.

## ADR-0021 — 2026-07-10 — 13F filer discovery: curated known-holders shortlist over search

**Status:** Accepted
**Decision:**
1. **V1 filer discovery uses a curated shortlist of known major institutional holders, not a discovery algorithm.** The pipeline maintains a static list of CIKs for top institutional filers (Vanguard, BlackRock, State Street, Fidelity, Capital Group, T. Rowe Price, etc. — ~15-25 filers). The 13F extractor iterates this list. No brute-force AUM scan, no EDGAR full-text search.
2. **List lives in `config/known_13f_filers.json`.** Format: `[{cik, name, rationale}]`. The `rationale` field documents why each filer was included (e.g. "top 5 by AUM, known holder of FOX/DIS/CMCSA"). Machine-readable, human-auditable.
3. **Expansion is iterative and manual.** When coverage gaps are found (e.g. a known activist holder missing from output), add their CIK to the list. No automated discovery infrastructure needed for v1.
**Context:** Three filer-discovery approaches were evaluated for v1:
- (a) **Brute-force top-N by AUM:** Download 13F filings from the top 200-500 institutional filers (by AUM), filter holdings for media CUSIPs locally. Reliable and comprehensive but over-fetches massively — most of the ~200-500 filers hold zero media securities. Runtime ~12-31 minutes for extraction alone, plus unnecessary load on SEC EDGAR.
- (b) **EDGAR full-text search (EFTS) for CUSIP:** Query EDGAR's EFTS for specific media CUSIPs to get a list of filers who reported holding them. Targeted, but EFTS search quality is inconsistent for structured data embedded inside XML info tables — untested in recon and potentially unreliable.
- (c) **Curated known-holders shortlist:** Maintain a static list of ~15-25 known major institutional holders. Phase 1 media companies are mostly large-cap (Fox, Disney, Comcast, NYT). The top ~20 institutional filers by AUM collectively hold the vast majority of institutional ownership in these companies. Recon spike (ADR-0020) confirmed this: Vanguard, BlackRock, State Street, and Fidelity alone covered the top holders for FOXA.
Option (c) chosen. Simplest approach with highest reliability. Zero discovery infrastructure to build or maintain. Predictable runtime (~3-8 minutes for 15-25 filers). The tradeoff — missing niche/activist holders — is acceptable for v1 under trail-end honesty (INV-19): if a holder isn't in the list, the trail ends there. Upgrade to brute-force or EFTS in v2 if coverage gaps become material.
**Alternatives considered:** Options (a) and (b) above. Also considered: (d) Hybrid — start with known holders, then run EFTS for any seed CUSIPs not covered. Rejected as over-engineered for v1; the shortlist alone covers the dominant holders.
**Implications:** T7 in the 13F extractor track (filer discovery) becomes "populate `config/known_13f_filers.json`" — a data task, not a code task. The 13F batch extractor (T5) iterates this list directly. No discovery module needed in `pipeline/`. If v2 needs broader coverage, the upgrade path is clear: replace the static list iteration with a brute-force or EFTS discovery step, feeding the same downstream extraction pipeline.

## ADR-0022 — 2026-07-11 — Entity discovery: hybrid multi-source approach over curated-only seed list

**Status:** Accepted (partially supersedes ADR-0021 scope — ADR-0021 still applies to 13F *filer* discovery; this ADR covers *media entity* discovery)
**Decision:**
1. **Media entity discovery uses a hybrid multi-source strategy, not a curated-only seed list.** The pipeline casts multiple nets across regulatory data sources, merges candidates via entity resolution, then verifies/enriches using extractor output. Curated seed entities (~18 anchor parents) become ground-truth test fixtures for measuring discovery quality, not the sole input.
2. **Discovery sources (Phase 1):** (a) SEC SIC code filtering — bulk `submissions/` data contains SIC codes; filter for core media SICs (2711 newspapers, 2721 periodicals, 4832 radio, 4833 TV, 4841 cable, 7812 motion picture production, etc.) yields ~1,286 entities from 272K total. (b) FCC LMS dump — broadcast licensees are media entities by definition. (c) 13F reverse scan — scan known institutional holders' portfolios, filter holdings by media SIC. (d) IRS 990 NTEE code filtering — nonprofit media orgs.
3. **Discovery is a pre-track** feeding into extractor tracks. Sequence: discovery (cast nets → entity resolution) → extractors (can unit-test independently, need discovery output for integration testing) → verification/enrichment (extractor results fill gaps, confirm matches).
4. **Provenance preserved at source-record granularity.** A unified entity record aggregates cross-source matches, but individual source records (SEC filing, FCC license, IRS 990) remain linked and independently queryable. No compilation step that loses source-level detail.
**Context:** Prior approach (ADR-0021 + design doc) assumed pipeline starts from a hand-curated list of ~100 outlets with manually gathered identifiers (CIK, ticker, CUSIP, FRN, EIN, domain). This works for verification but doesn't scale and can't discover entities the curator didn't think of. Testing showed SEC's bulk `submissions/` data (272K files, already downloaded) contains SIC codes — filtering for core media SICs returns ~1,286 companies, including most known anchor entities (Fox, Disney, Comcast, NYT, Nexstar, Sinclair, Scripps, Salem, Cumulus, Audacy, etc.).
**Known gaps in SIC-only discovery:** (a) Companies that merged, went private, or delisted (Gannett/GateHouse, Tribune) disappear from active SIC listings. (b) Tech companies classified under software SICs (7372) despite being media companies (streaming platforms). (c) Private media companies have no SEC filing. (d) Subsidiaries may use parent's SIC, not their own media SIC. These gaps motivate the hybrid approach — cross-source coverage compensates for single-source blind spots.
**Alternatives considered:** (a) Curated-only seed list — high confidence per entry but labor-intensive, doesn't discover unknowns. (b) Single-source SIC scan — misses private companies, nonprofits, FCC-only licensees. (c) Full automated discovery with ML classification — over-engineered for Phase 1.
**Implications:** New discovery pre-track created (`_model/tracks/planned/entity-discovery.md`). T7 in 13F extractor track remains unchanged (13F *filer* discovery is a separate concern — which institutional investors to scan, not which media companies exist). Contracts kept simple and flexible during discovery prototyping — final shapes emerge from testing. `config/known_13f_filers.json` scope unchanged.

## ADR-0023 — 2026-09-19 — FCC name-under-FRN: distinguish renames from transfer counterparties

**Status:** Accepted (refines INV-22 name-change-under-stable-FRN)
**Decision:** When collecting the many `apar_legal_party_name` spellings that share one FRN in `app_party.dat`, treat only names sharing the modal name's **distinctive tokens** as aliases (genuine renames, INV-22). Names with no distinctive-token overlap are **quarantined** as `possible_counterparties` (an entity attribute), never folded into the entity's identity. Quarantine ≠ drop: they surface as labeled data (INV-20).
**Context:** FRN 0005795067 (Fox Television Stations) carries 1160 "FOX…" rows plus a tail — TRIBUNE (12), NEXSTAR (2), KTVU (2). Fox never owned Tribune/Nexstar; these are counterparties on station-transfer applications (or FCC mis-keys). Aliasing them asserted "Nexstar is another name for Fox" — a false identity that would then poison the SEC↔FCC merge (ADR-0025) by fuzzy-matching Nexstar's real SEC entity into Fox.
**Alternatives considered:** (a) Use `apar_name_change_form_175_ind` (FCC's own name-change flag) — rejected as primary lever: unreliable in practice; distinctive-token overlap is self-contained and testable. (b) Frequency threshold alone — brittle; a legitimate low-volume rename would be dropped. (c) Keep all as aliases — the bug.
**Implications:** Failure mode is safe: a total-rebrand rename with no shared tokens is quarantined (labeled uncertain), never silently mis-merged. Quarantined counterparties are latent transfer/ownership edges (a real `relationship` source later — see TODO). Implemented in `extractors/fcc/name_core.py` + `extract.py`.

## ADR-0024 — 2026-09-19 — Address is a positive-only tiebreaker in cross-source matching, never a requirement or veto

**Status:** Accepted
**Decision:** In SEC↔FCC entity matching, a corroborating address may lift a MEDIUM name match to HIGH, but address **disagreement never vetoes** a match and a **shared address never forces** one. The load-bearing discriminator is name WRatio gated by the distinctive-token guard (ADR-0025), not address.
**Context:** For Fox the two addresses disagree by design — SEC business address = corporate HQ (10201 W Pico Blvd, LA); FCC party address = the licensee's DC regulatory counsel (444 N Capitol St, Washington DC). This is normal for broadcasters. Requiring address agreement would reject a correct match; using shared address as a match key would falsely merge every unrelated licensee that shares one DC law firm.
**Alternatives considered:** (a) Address as a required feature — fails Fox and most broadcasters. (b) Address as a blocking key — mass false merges via shared counsel/agent addresses (CT Corporation, law firms). (c) Ignore address entirely — loses a genuine signal when HQ addresses do coincide.
**Implications:** `resolution/cross_source.py` computes `address_agreement` only when both sides carry a parseable address, and uses it positive-only. FCC extractor does not currently promote address to the entity (it is regulatory-counsel data), so agreement is usually not evaluable — acceptable.

## ADR-0025 — 2026-09-19 — Cross-source identity merge is a non-official "Likely"-tier inference, recorded as provenance

**Status:** Accepted (implements design/entity-discovery.md "never merge silently"; relates to INV-10, two-axis tier)
**Decision:**
1. A cross-source identity merge ("this FCC licensee IS this SEC filer") is a **probabilistic inference**, emitted as `source_official=FALSE` + `extraction_method=automated` — the first non-official datum the pipeline produces. This is not an INV-10 violation: INV-10 bars unofficial *sources* (aggregators/news); the two-axis model reserves the graded "Likely" tier for our own inferences. The server's default Official-only view hides it until the tier facet is opened.
2. **Never merge silently.** Merging attaches the other source's external_ids to the kept entity; every attached id carries `merge_confidence` + `merge_method`, and one provenance record per attached id documents the assertion (anchor payload: both sides' keys, WRatio, shared tokens, address agreement). `merge_entities()` raises if asked to merge without a decided tier.
3. **Match policy (provisional).** Distinctive-token overlap REQUIRED (false-positive guard); WRatio tier on top: ≥92 HIGH, ≥82 MEDIUM, else no merge. Cutoffs are placeholders until the empirical D3 floor is set.
**Context:** SEC (CIK/EIN) and FCC (FRN) namespaces are disjoint — no deterministic bridge (handoff 2026-09-18). Verified on real Fox: name-only WRatio scored unrelated GANNETT at 85 (pre-normalization); the distinctive-token guard rejects it (zero overlap), and full-string WRatio also separates two *real* Fox entities (Fox TV vs Fox Sports Networks, WRatio 47.6) that share the `{FOX}` token.
**Alternatives considered:** (a) Silent merge into one entity — destroys the trust chain; the identity hop becomes an invisible weak link. (b) Treat merge as `official` — a fuzzy inference is categorically not deterministic. (c) Distinctive-token guard alone — insufficient (Fox TV vs Fox Sports both pass the guard; WRatio separates them).
**Implications:** New `sources` row `pipeline_resolution` (`source_official=0`). Merge provenance uses a derivation `source_document` (`doc_type=cross_source_merge`, no access_links). Validation rule to add: "every external_id with merge_confidence has a merge provenance record" (was P3). Implemented in `resolution/cross_source.py` + `resolution/names.py`.
